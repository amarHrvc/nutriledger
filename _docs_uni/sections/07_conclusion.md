# 7. CONCLUSION

## 7.1. Future Work

The current NutriBase MVP covers the three core feature groups required for clinical operation: user and authentication management, patient record management, and visit tracking. While this constitutes a functional and deployable system, the clinical domain it targets is considerably broader. The planned post-MVP roadmap extends the platform through eight additional feature groups.

Groups 4 through 6 introduce structured clinical measurements. Group 4 adds vital signs recording per visit — blood pressure, pulse rate, body temperature, weight, height, and computed BMI — with automatic flagging of values outside normal ranges. Group 5 introduces a medication management module, allowing doctors to maintain a list of active and discontinued medications per patient with dosage and frequency. Group 6 enables laboratory result logging, associating lab parameters, measured values, units, and reference ranges with specific visits, and providing a chronological view across the patient's history.

Groups 7 through 9 build clinical support and operational tools on top of the core record. Group 7 introduces dietary and lifestyle recommendations attached to visits, with configurable expiry dates. Group 8 adds a reminder system for scheduled lab tests, follow-up consultations, and check-ups, surfaced as a dashboard widget for clinical staff. Group 9 provides summary dashboards — a clinic-level overview of active patients, upcoming visits, and flagged abnormal values, as well as a patient-level mini-overview widget accessible during a consultation.

Beyond structured data, the platform is designed to support an AI and automation layer. A rule-based nutritional risk scoring engine would derive a risk level from existing patient data. Workflow automation via n8n would handle inactivity alerts and pre-visit briefing generation. The most impactful planned feature is a doctor assistant — a retrieval-augmented generation chatbox using the Laravel AI SDK and Claude as the underlying model, giving doctors the ability to ask natural-language questions about a specific patient's history, with responses streamed back via server-sent events. Voice-to-notes transcription using the Whisper API is also planned, reducing the manual effort of documenting visit observations.

## 7.2. Final Words

The development of NutriBase provided practical exposure to a range of engineering challenges that are difficult to appreciate from academic study alone. Designing a stateless REST API with three-layer authorization — middleware, form requests, and policies — required careful attention to the interaction between Laravel's routing system, its service container, and the Sanctum token lifecycle. The dual-entity patient creation flow, which must atomically create a patient record and an associated socioeconomic profile within a single database transaction, was the most complex implementation task and led to the introduction of the Service Layer pattern as a structural solution.

Coordinating a frontend and backend developed in parallel also required discipline: the API contract had to be stable enough for the React SPA to consume before all endpoints were implemented, which reinforced the value of defining response shapes and error structures upfront. The test-driven development approach, using Pest with an in-memory SQLite database, provided fast feedback cycles and caught several authorization edge cases — including cross-patient data access — that would have been difficult to detect through manual testing. The result is a system that is not only functional but verifiably correct with respect to its security requirements, and one that is structured to support the extended clinical feature set planned for future releases.
