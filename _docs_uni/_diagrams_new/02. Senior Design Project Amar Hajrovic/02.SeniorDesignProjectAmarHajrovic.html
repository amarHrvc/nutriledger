ABSTRACT

Nutrition clinics/healthcare professionals commonly rely on paper-based records or generic office software that lacks role-based access control, structured patient profiles, and a traceable history of clinical encounters. This project presents NutriBase, a web-based clinical information system that addresses these gaps through a decoupled architecture: a  stateless RESTful API built with Laravel 12 and secured with token-based authentication, consumed by a React TypeScript single-page application. The system enforces three-layer authorisation across three user roles - administrator, doctor, and patient — and covers following feature groups: user management, patient records, visit tracking, and AI-powered diet plan generation.

  1. INTRODUCTION

Clinical nutrition management is a discipline that requires accurate, longitudinal records of patient health — covering not only medical data such as blood type, allergies, and visit notes, but also the social determinants of health such as employment status, household income, dietary restrictions, and food security. In practice, many nutrition clinics and general practitioners still rely on paper-based records or generic office software that was not designed for clinical workflows. These tools offer no role-based access control, no structured patient profile, and no mechanism for tracking visit history alongside socioeconomic context. The result is fragmented information, increased risk of data loss, and no clear audit trail of clinical encounters.

The aim of this project is to design and implement NutriBase, a web-based clinical information system that addresses these gaps. NutriBase provides a centralised platform for three types of users: administrators who manage system access and oversee all records, doctors who register and manage patient profiles and document clinical visits, and patients who have read-only access to their own data. The system enforces strict role-based access control so that no user can view or modify data outside their permitted scope, and it captures both clinical and socioeconomic patient data in a structured, queryable form.

The proposed solution follows a decoupled architecture: a stateless RESTful API built with Laravel 12(Laravel - The Clean Stack for Artisans and Agents, n.d.) and secured using Laravel Sanctum(Laravel Sanctum, n.d.) token-based authentication forms the backend, while a Next.js 15 application built with React and TypeScript.. The two layers communicate exclusively over HTTPS using JSON-formatted request and response bodies. This separation of concerns allows the frontend and backend to be developed, tested, and deployed independently. The current implementation covers the following feature groups: user management, patient records, visit tracking, and AI-powered diet plan generation.

  1. SYSTEM ANALYSIS

2.1. System Overview

The following subsections define the product's scope, intended users, known constraints, and measurable success criteria.

2.1.1. Product Perspective

NutriBase is a web-based clinical information system designed to support multi-role workflows in nutrition clinics and general practice settings. The system exposes a stateless RESTful API as the backend layer, which is consumed by a React TypeScript single-page application. The API and SPA communicate exclusively over HTTPS using JSON request and response bodies. Authentication is token-based: on login, the server issues an opaque Sanctum token that the client includes as a Bearer header on all subsequent requests. The system does not use session cookies, making it suitable for deployment across separate origins.

The platform manages four core entities: user accounts (with role assignments), patient profiles, patient socioeconomic profiles, and visit records. Role-based access control is enforced at three layers — route middleware, form request authorization, and policy classes — ensuring that each user type can only access and modify data within their permitted scope.

2.1.2. Target Audience

Admin — The system administrator. Admins have full access to all resources: they create, edit, deactivate, restore, and permanently delete user accounts; they manage all patient records including soft-delete and restore operations; and they can delete visit records. Admins benefit from a centralised control point for system access and data governance.

Doctor (Doktor) — Clinical staff responsible for patient care. Doctors can register and manage patient profiles, view all active patients, and create visit records documenting their clinical encounters. Doctors benefit from a structured, searchable patient record that includes socioeconomic context alongside clinical data.

Patient - The end user receiving care. Patients have read-only access restricted to their own profile and their own visit history. They cannot view other patients' records, cannot create or modify any data, and cannot access user management functions. Patients benefit from transparent access to their own medical information.

2.1.3. Project Constraints and Risks

Timeline constraint. The project is structured around three university milestones: M1 (April 5 2026, documentation only), M2 (May 3 2026, Release 1: auth and patient management), and M3 (June 7 2026, Release 2: visits, patterns, tests, deployment). The interval between M2 and M3 is five weeks, during which the visit API, design patterns, test coverage, and deployment must all be completed. A delay in M2 delivery directly compresses the time available for M3.

Dual-entity creation complexity. Registering a new patient requires atomically creating both a Patient record and an associated PatientSocioeconomic record in a single database transaction. If either insert fails, both must be rolled back. This is the most complex data flow in the system and introduces the risk of partial data corruption if not handled correctly.

CORS configuration risk. The React SPA and the Laravel API are deployed to separate origins. Misconfigured CORS headers — particularly the allowed origin, allowed headers, or preflight response — would silently block all API requests from the frontend without obvious error messages in the application UI.

Cross-patient data leakage. If the patient policy is not correctly enforced, an authenticated patient could request another patient's profile or visit records by guessing their ID. This is a critical security risk in a medical context. It is mitigated by explicit policy checks in every controller action that touches patient-scoped data, and by explicit test cases that verify 403 responses for cross-patient access attempts[d][e].

2.1.4. Success Criteria

The following measurable criteria define a successful delivery:

  • All API endpoints Auth - 4, Users (CRUD + restore + force-delete) - 6, Patients - 5, Visits per patient - 6, Vital signs - 5, Diet plans - 5 ) return the correct HTTP status codes for all role combinations. 
  • Three-layer authorization is in place for every protected endpoint: auth:sanctum middleware, authorize() in the form request, and a named policy method.
  • Unauthenticated requests to protected endpoints return HTTP 401. Requests from unauthorized roles return HTTP 403. Patients attempting to access other patients' records return HTTP 403.
  • A minimum of 5 Pest HTTP feature tests pass, covering authentication, role-gated access, and at least one validation failure case.
  • The application is accessible at a publicly reachable URL on Railway. 
  • The React SPA renders the login page, patient list, patient profile, visit history, vital signs and diet plans without JavaScript errors.

2.2. Functional Requirements

Functional requirements (Kumari, 2025) define the specific behaviors, services, and tasks that a software system must provide to satisfy user needs. They outline "what" the system is supposed to do under specific conditions. Below are functional requirements of this system.

  1. User login

As a user (admin, doctor, or patient), I can log in with my email and password so that I can access the system and perform actions permitted by my role.

Acceptance criteria:

  • Valid credentials grant access and return a session token along with the authenticated user's name, email, and role.
  • An inactive or deactivated account is rejected with the message "Account is deactivated"; the user cannot proceed.
  • The system does not disclose whether a given email address exists in the system.

  1. Session token uniqueness

As a user, I receive a unique session token on each successful login so that multiple active sessions can coexist without interfering with each other.

Acceptance criteria:

  • Each login event produces a distinct token.
  • A second login from the same account does not invalidate a previously issued token.

  1. Logout

As an authenticated user, I can log out so that my current session token is immediately invalidated and my account is secured.

Acceptance criteria:

  • After logout, the revoked token is rejected for all subsequent requests.

  1. Invalid credentials feedback

As a user, I receive a clear error message when I provide an incorrect email or password so that I know my login attempt failed.

Acceptance criteria:

  • The error message for wrong credentials differs from the message for a deactivated account, but neither reveals whether the email exists.
  1. Create user account

As an admin user, I can create a new user account by providing a name, email, password, and role so that staff and patients can access the system.

Acceptance criteria:

  • The email address must be unique across all accounts.
  • The role must be one of the three recognised roles (admin, doctor, patient); any other value is rejected.
  • Only admins can create accounts; any other authenticated role is denied.

  1. View user list (admin)

As an admin user, I can view a list of all user accounts — including deactivated ones — so that I have full visibility over system access.

Acceptance criteria:

  • The list includes both active and soft-deleted accounts.

  1. View user list (doctor)

As a doctor user, I can view a paginated list of active user accounts so that I can look up colleagues and patient accounts.

Acceptance criteria:

  • Only active (non-deactivated) accounts are included.
  • Patient-role users are denied access to the user list.

  1. View single user

As an admin user, I can view the full profile of any user, including deactivated ones. As a doctor or patient, I can view the profile of any active user, subject to policy.

Acceptance criteria:

  • Admins can retrieve soft-deleted user records that are invisible to other roles.
  1. Admin updates any user profile

As an admin user, I can update the profile information of any user account so that I can keep user data accurate.

Acceptance criteria:

  • Any subset of name, email, password, or role can be updated in a single request.
  • Fields not included in the request are not modified.
  • Only admins can perform this action on other users' accounts.

  1. User updates own profile

As a user, I can update my own name, email, or password so that I can keep my details current.

Acceptance criteria:

  • Only the fields included in the request are modified; unmentioned fields are left unchanged.

  1. Role self-assignment blocked

The system shall prevent any user from changing their own role assignment so that privilege escalation and self-demotion are blocked.

Acceptance criteria:

  • Any request from a user that includes a role change targeting their own account is rejected or silently ignored.
  • This restriction applies to all roles, including admins.

  1. Deactivate user account

As an admin, I can deactivate a user account so that the user loses access while their data is retained in the system.

Acceptance criteria:

  • The account is soft-deleted; its data is preserved and restorable.
  • An admin cannot deactivate their own account.
  • Non-admin users cannot deactivate any account.

  1. Token revocation on deactivation

At the moment a user account is deactivated all active session tokens belonging to a user will be revoked so that a deactivated user cannot continue any active session.

Acceptance criteria:

  • Any in-flight request using a previously valid token from a newly deactivated account is rejected.

  1. Restore deactivated user

As an admin user, I can restore a previously deactivated user account so that the user can authenticate again.

Acceptance criteria:

  • After restoration the user can log in and access the system normally.
  • Only admins can restore accounts.

  1. Permanently delete user

As an admin user, I can permanently delete a user account and all associated data so that the system can be fully cleaned up when required.

Acceptance criteria:

  • All records associated with the user are removed from the database.
  • Only admins can perform this action.

  1. Register a new patient

As an admin or doctor user, I can register a new patient by providing their personal details (first name, last name, date of birth, gender, phone number, and address) so that their clinical record exists in the system.

Acceptance criteria:

  • All required personal fields must be present; missing fields are rejected.
  • Patients and unauthenticated users cannot register new patients.

  1. Record clinical medical data

As an admin or doctor user, I can record optional clinical data for a patient — including blood type, allergies, and general medical notes — so that clinically relevant information is stored alongside their profile.

Acceptance criteria:

  • All clinical fields are optional; omitting any of them does not cause an error.
  • Clinical data is stored directly on the patient record.

  1. Record socioeconomic profile

As an admin or doctor user, I can record an optional socioeconomic profile for a patient - including employment status, income level, living arrangement, health insurance, lifestyle factors, and dietary restrictions — so that the full social context of the patient is available for clinical decision-making.

Acceptance criteria:

  • The socioeconomic profile is an independent record linked to the patient.
  • All socioeconomic fields are optional; omitting any does not cause an error.
  • If a socioeconomic profile already exists, a subsequent update merges the provided fields without clearing unmentioned ones.

  1. Atomic patient registration

The system shall treat the creation of a patient and their associated socioeconomic profile as a single atomic operation so that either both records are persisted or neither is.

Acceptance criteria:

  • If any part of the registration fails after the patient record has been written, the entire operation is rolled back and no partial data remains in the database.

  1. View patient list

As an admin or doctor user, I can view a paginated list of all active patient records so that I can efficiently browse and manage patients.

Acceptance criteria:

  • Only active (non-deactivated) patient records are included.
  • A patient-role user who accesses the list sees only their own record.

  1. Search patients by name

As an admin or doctor user, I can search the patient list by first or last name so that I can quickly locate a specific patient.

Acceptance criteria:

  • The search is case-insensitive and matches partial names.
  • An absent or empty search term returns the full list without filtering.
  1. View patient full profile

As an admin or doctor user, I can view the complete profile of any active patient — including personal details, clinical medical data, and socioeconomic profile — so that I have a full picture when managing their care.

Acceptance criteria:

  • The response includes the patient's linked user account, clinical fields, and socioeconomic record.
  • A request for a non-existent patient is rejected.

  1. Patient views own profile only

As a patient user, I can view my own profile so that I can review my own data, and I am prevented from viewing any other patient's profile so that my privacy is protected.

Acceptance criteria:

  • Accessing another patient's profile is denied without revealing whether that record exists.
  1. Update patient record

As an admin or doctor user, I can update a patient's personal details, clinical data, or socioeconomic profile, where only the fields I include are modified, so that partial updates do not overwrite unrelated data.

Acceptance criteria:

  • Fields not present in the request retain their existing values.
  • If a socioeconomic object is included it is upserted; other patient fields are unaffected.
  • The update is wrapped in a database transaction; a failure during socioeconomic update rolls back the patient update as well.
  • Patient-role users cannot update any patient record.

  1. Deactivate patient record

As an admin or doctor user, I can deactivate a patient record so that it is removed from the active list while the patient's visit history is preserved.

Acceptance criteria:

  • The patient record is soft-deleted; all associated visit records remain intact.
  • The deactivated patient no longer appears in the patient list.

  1. Create a visit record

As a doctor user, I can create a visit record for an active patient by specifying the visit date, time, and clinical notes so that the encounter is formally documented.

Acceptance criteria:

  • Visit time is optional.
  • Clinical notes are optional.
  • Patient-role users and unauthenticated requests are rejected.

  1. Visit attributed to creating doctor

The system shall automatically associate each visit record with the doctor who created it, and this association cannot be overridden by a doctor, so that authorship integrity is maintained.

Acceptance criteria:

  • The doctor recorded on a visit always equals the authenticated user who submitted the request, regardless of any doctor identifier supplied in the payload, unless the requesting user is an admin.
  • An admin may explicitly assign a visit to a specific doctor at creation time.

  1. Global visit schedule

As an admin or doctor user, I can view a paginated schedule of visits across all patients so that I can monitor upcoming and past encounters.

Acceptance criteria:

  • For admins the schedule includes all doctors' visits; for doctors it includes only their own visits.
  • Results are ordered so that today's and future visits appear before past visits, then sorted by date and time.

  1. View patient visit history

As an admin or doctor user, I can retrieve the complete visit history of a patient ordered from most recent to oldest so that I can review the patient's clinical timeline.

Acceptance criteria:

  • Results are paginated and ordered by date descending.

  1. Patient views own visit history only

As a patient user, I can view my own visit history and am prevented from viewing any other patient's visit history so that my medical records remain private.

Acceptance criteria:

  • Accessing another patient's visits is denied.
  1. View single visit

As an admin, doctor user, or the owning patient, I can view the full detail of a specific visit including the attending doctor's information.

Acceptance criteria:

  • A request for a visit that belongs to a different patient than specified is rejected as not found.
  • A patient can only view their own visits; accessing another patient's visit is denied.

  1. Doctor edits own visit

As a doctor user, I can edit the date, time, and clinical notes of a visit that I personally created so that I can correct or supplement my own documentation.

Acceptance criteria:

  • A doctor may only edit visits they created; attempting to edit another doctor's visit is denied.
  • The visit date must not be set to a future date.
  • Only the fields included in the request are modified.

  1. Admin edits any visit

As an admin user, I can edit any visit record regardless of which doctor created it so that administrative corrections can be made when necessary.

Acceptance criteria:

  • Admins are not restricted by visit ownership.

  1. Permanently delete a visit

As an admin user, I can permanently delete a visit record so that erroneous entries can be removed cleanly.

Acceptance criteria:

  • Deleting a visit does not affect the associated patient record or any other visits.
  • A visit ID belonging to a different patient than specified is treated as not found.
  • Doctor and patient roles cannot delete visits.

  1. Record vital signs for a visit

As an admin or doctor user, I can record a set of vital signs for a specific visit - including blood pressure, heart rate, temperature, weight, height, and BMI - so that clinical measurements are linked to the encounter.

Acceptance criteria:

  • All vital sign fields are optional; at least one value should be provided.
  • Only one vital signs record can exist per visit; attempting to record a second set for the same visit is rejected.

  1. View vital signs for a visit

As an admin, doctor user, or the owning patient, I can view the vital signs recorded for a specific visit so that the clinical measurements for that encounter are accessible.

Acceptance criteria:

  • The response includes clinically computed flags identifying any values outside normal reference ranges (see FR-VS5).
  • If no vital signs were recorded for the visit, the request is treated as not found.

  1. Update vital signs

As an admin or doctor user, I can update the vital signs recorded for a visit so that measurement errors can be corrected.

Acceptance criteria:

  • Only the fields included in the request are modified.

  1. Delete vital signs

As an admin user, I can delete the vital signs record for a visit so that erroneous measurements can be removed.

Acceptance criteria:

  • Deleting vital signs does not affect the visit record itself.
  • Doctor and patient roles cannot delete vital sign records.

  1. Automatic clinical flag computation

The system shall automatically evaluate each vital sign value against standard clinical reference ranges and flag any value that falls outside the expected range so that clinicians are immediately alerted to abnormal measurements.

Accepted reference ranges:

  • Systolic blood pressure: 90–140 mmHg
  • Diastolic blood pressure: 60–90 mmHg
  • Heart rate: 50–100 bpm
  • Temperature: 36.0–37.5 °C
  • BMI: flagged as underweight (< 18.5), overweight (≥ 25.0), or obese (≥ 30.0)

  1. View patient vital signs history

As an admin or doctor user, I can view a chronological history of a patient's vital signs across all visits, optionally filtered by a date range, so that I can track clinical trends over time.

Acceptance criteria:

  • Results are paginated and ordered by visit date descending.
  • An optional start date and end date filter narrows the results to the specified range.

  1. Request AI-generated diet plan

As an admin or doctor user, I can request an AI-generated personalized diet plan for a patient so that a tailored nutritional recommendation is produced based on the patient's clinical and socioeconomic profile.

Acceptance criteria:

  • The request is accepted immediately and the plan is queued for asynchronous generation.
  • The requesting user is recorded as the plan's author.
  • Patient-role users cannot request diet plan generation.

  1. Asynchronous AI generation

Admin/Doctor request shall generate diet plans asynchronously using an AI language model, retrying once on validation failure, so that the main application remains responsive during generation.

Acceptance criteria:

  • The generated plan includes: a clinical rationale, daily calorie target, nutritional goals (protein, carbohydrates, fat in grams), a seven-day meal plan (breakfast, lunch, dinner, snack per day), and clinical warnings.
  • On successful generation the plan status transitions to completed.
  • If the AI response fails validation after two attempts, the plan status transitions to failed and a failure reason is recorded.

  1. View diet plan list

As an admin or doctor user, I can view the list of all diet plans generated for a patient, ordered from most recent to oldest, so that I can review the history of recommendations.

Acceptance criteria:

  • Plans are listed regardless of their status (pending, completed, failed).
  • Patient-role users cannot view the diet plan list.

  1. View full diet plan

As an admin or doctor user, I can view the full content of a specific diet plan — including rationale, calorie target, nutritional goals, daily meal schedule, warnings, and any edits — so that I can review the complete recommendation.

Acceptance criteria:

  • A plan belonging to a different patient than specified in the URL is treated as not found.

  1. Edit a completed diet plan

As an admin or doctor user, I can edit the content of a completed diet plan so that I can adjust or supplement the AI-generated recommendation with my clinical judgement.

Acceptance criteria:

  • Only plans with completed status can be edited; editing a pending or failed plan is rejected.
  • The edit is recorded: the editing user and the time of edit are stored alongside the plan.

  1. Send diet plan by email

As an admin or doctor user, I can send a completed diet plan to the patient's registered email address so that the patient receives a copy of their nutritional plan.

Acceptance criteria:

  • Only a plan with completed status can be sent; attempting to send a pending or failed plan is rejected.
  • A patient with no email address on record cannot receive a plan; this condition is communicated to the requester.
  • The delivery is dispatched asynchronously; the system acknowledges the request immediately.

  1. IMPLEMENTATION

4.1. Implementation Overview

NutriBase is implemented as a decoupled two-tier system: a stateless RESTful API on the backend and a React TypeScript single-page application on the frontend. The backend is built with Laravel 12(Laravel - The Clean Stack for Artisans and Agents, n.d.) running on PHP 8.4 (PHP, n.d.) and uses Laravel Sanctum (Laravel Sanctum, n.d.) for token-based authentication. All business logic is encapsulated in a Service Layer, data access is abstracted through the Repository Pattern, and domain events are handled via the Observer Pattern. The frontend is a next-js (Next.js by Vercel - The React Framework, n.d.) React application written in TypeScript(JavaScript with Syntax for Types, n.d.) using Vuexy (Vuexy - Bootstrap HTML Admin Template, 2023) template. The two layers communicate exclusively over HTTPS, exchanging JSON payloads that conform to a consistent envelope structure: { "data": {...}, "message": "..." } for success responses and { "message": "...", "errors": {...} } for validation failures.

4.2. Backend Technologies

PHP 8.4 (PHP, n.d.) is the server-side language underpinning the entire backend. It was chosen because Laravel 12 requires PHP 8.2 or higher, and 8.4 is the current stable release.

Laravel 12 is the primary backend framework. It provides the MVC structure, Eloquent ORM, route model binding, form request validation, and policy-based authorization used throughout the application. Laravel's service container and dependency injection system make it straightforward to introduce the Service Layer and Repository patterns without framework friction. Its streamlined bootstrap structure (introduced in Laravel 11) reduces configuration overhead.

Laravel Sanctum provides lightweight token-based authentication for the SPA. On login, Sanctum issues an opaque personal access token that the React client stores and attaches as a Bearer header on all subsequent requests. Sanctum was chosen over Passport because the application does not require OAuth2 flows — simple token issuance and revocation is sufficient for the clinical SPA use case.

(PostgreSQL, 2026) is the relational database. The schema consists of four core tables: users, patients, patient_socioeconomic, and visits. Foreign key constraints enforce referential integrity across the one-to-one and one-to-many relationships. SQLite is used in-memory during automated testing to provide fast, isolated test runs without requiring a running database server.

Pest 4 (Maduro, n.d.) is the testing framework. All API behaviour is verified through Pest feature tests that make real HTTP requests against the application using an in-memory SQLite database and the RefreshDatabase trait. Tests cover happy paths, validation failures, and all role-based authorization combinations. The actingAs() helper is used to authenticate requests as specific users without going through the login endpoint.

Laravel Pint (Laravel Pint, n.d.)enforces PSR-12 code style across all PHP files. It is run with the --dirty flag as part of the development workflow to format only files that have changed, keeping the codebase consistent without full-suite overhead.

Larastan (GitHub - Larastan/larastan: ⚗️ Adds Code Analysis to Laravel Improving Developer Productivity and Code Quality, n.d.) provides static analysis at level 5 using PHPStan's engine extended with Laravel-specific rules. It detects type mismatches, undefined properties on Eloquent models, and incorrect return types before tests are run, catching a category of bugs that tests alone do not cover.

4.3. Frontend Technologies

React 18(React, n.d.) i[q]s the UI library. Its component model allows each page (login, patient list, patient profile, visit history) to be developed and tested independently. React's unidirectional data flow makes it straightforward to reason about which server state drives which UI elements.

TypeScript(JavaScript With Syntax For Types, n.d.)[r][s] adds static typing to the JavaScript frontend. API response shapes are defined as TypeScript interfaces, ensuring that components reference only fields that the API actually returns. This eliminates an entire class of runtime errors caused by field name mismatches between the frontend and backend contract.

Next.js(Next.js by Vercel - The React Framework, n.d.) [t][u]is the React framework serving as both the application shell and build toolchain. It provides file-based routing through the App Router, a built-in development server with fast refresh, and optimised production builds without separate bundler configuration. Next.js was chosen as the Vuexy template's foundation because it covers routing, rendering, and bundling in a single dependency, and aligns with the current direction of the React ecosystem.

4.4. Integrations and Services

Railway is the deployment platform for the Laravel API backend. Both are PaaS providers that support PHP and PostgreSQL, handle TLS termination, and allow environment variables to be managed through a web dashboard. The Laravel application is deployed as a containerised service; database migrations run automatically as a release command on each deployment.

CORS (Laravel configuration). The React SPA and the Laravel API are hosted on separate origins (different ports in development, different subdomains in production). Laravel's built-in CORS middleware is configured in config/cors.php to allow the SPA origin, the required HTTP methods (GET, POST, PUT, PATCH, DELETE), and the Authorization and Content-Type headers. In production, the allowed origin is restricted to the specific SPA domain to prevent cross-site request forgery.

  1. AI-ASSISTED SPECIFICATION-DRIVEN DEVELOPMENT

5.1. Motivation and Problem Statement

The emergence of large language model (LLM)-powered coding assistants has introduced a new risk in software engineering practice: vibe coding — the habit of issuing a loosely worded prompt to an AI and accepting whatever code is produced, without first defining requirements, validating assumptions, or establishing any traceability between the stated need and the resulting implementation. While this approach can produce rapid initial output, it tends to accumulate undocumented decisions, unclear scope boundaries, and untestable behaviour. The resulting system may function in demonstration conditions while being structurally unsound for production use.

NutriBase adopts the opposite position. AI tools are used extensively throughout the development process — for generating boilerplate, resolving ambiguities, researching SDK patterns, and producing first drafts of specification documents — but they operate within a structured, human-directed workflow. The human developer remains the architect: defining what is needed, approving design decisions, and reviewing every artifact before it advances to the next phase. The AI assists in executing those decisions efficiently and consistently.

This methodology is formalised in the project using a tool called speckit (Spec Kit - AI-Powered Specification-Driven Development Toolkit, n.d.), a specification workflow system. The workflow enforces a strict sequence: a feature cannot be implemented until it has been formally specified, and it cannot be planned until the specification has been reviewed and all unknowns have been resolved. The sections below describe the workflow stages and illustrate each with a concrete example drawn from Feature 014: the AI Diet Plan Generator.

5.2. Workflow Overview

The speckit workflow consists of four sequential phases. Each phase produces a named artifact stored in the feature's specification directory. No phase may begin until all artifacts from the preceding phase are complete.        

Table 5.1 Speckit workflow overview

The workflow is designed so that the artifact produced by each phase contains enough information to allow a developer (human or AI) to execute the next phase without requiring verbal explanation. This property — that all decisions are written down before implementation begins — is what distinguishes specification-driven development from ad-hoc AI-assisted coding.

5.3. Phase 1: Feature Specification (/speckit.specify)

The specification phase begins with a natural language description of the feature. The developer provides this description, which becomes the authoritative input to the specification process. The tool produces a spec.md file organised into mandatory sections: User Scenarios (with acceptance criteria), Functional Requirements, Key Entities, Success Criteria, and Assumptions.

Principles enforced by the specification phase

Technology agnosticism. The specification describes what users need, not how the system will deliver it. References to specific frameworks, languages, or database engines are prohibited. This constraint ensures that the specification remains stable even if implementation choices change.

Testability of requirements. Every functional requirement is written in the form "System MUST [specific, observable behaviour]" and every user scenario includes acceptance criteria in the Given/When/Then format. A requirement that cannot be expressed this way is a sign that it is not yet clear enough to implement.

Bounded unknowns. If a critical design decision cannot be resolved from the feature description alone, it is marked with a [NEEDS CLARIFICATION: ...] tag. The specification phase enforces a maximum of three such markers; all must be resolved before planning begins. This prevents the planner from inheriting ambiguity.

Example: Feature 014 specification

The diet plan feature was specified from the following developer-provided description:

“A doctor can generate a 7-day AI-powered diet plan for a patient. The system returns an acknowledgement immediately, generates the plan in a background job, and stores it in a history table. Only doctors and admins can access diet plan endpoints.”

The /speckit.specify command expanded this into a spec.md containing twelve functional requirements, four user stories covering generation, history browsing, failure handling, and access control, and six measurable success criteria.

The specification was validated against a quality checklist covering content quality, requirement completeness, and feature readiness before advancing to the planning phase.

5.4. Phase 2: Implementation Planning (/speckit.plan)

The planning phase reads the spec.md and produces four artifacts:

  • research.md,
  • data-model.md,
  • contracts/ directory,
  • plan.md.

Each addresses a different aspect of the transition from requirement to design.

For Feature 014, nine decisions were recorded (D1 through D9), some of them covering topics including:

D1 — SDK installation: laravel/ai with the Open AI provider was chosen;

D2 — Job architecture: A custom GenerateDietPlanJob was chosen over the SDK's built-in ->queue() fluent API, because the manual retry-and-status-transition logic required imperative control flow that the SDK's callback-based API does not provide cleanly.

D3 — Retry strategy: Manual retry loop inside handle() (maximum two attempts) rather than Laravel's automatic job retry mechanism, to keep the pending status consistent throughout both attempts.

D6 — Structured output API: The correct SDK schema signature (schema(JsonSchema $schema): array) was confirmed through the project's internal research corpus, which contained a full SDK knowledge index compiled in an earlier research session.

5.5. Phase 3: Task Generation (/speckit.tasks)

The task generation phase reads all planning artifacts — plan.md, spec.md, data-model.md, contracts/, and research.md — and produces a tasks.md file that decomposes the implementation into individually executable, independently verifiable steps. Each task specifies a unique identifier, a parallel implementation flag, a user story label, a concrete action, and an exact file path. This format is designed so that any task can be handed to a developer or an AI coding agent without requiring additional context.

Tasks are structured and enforced by tasks generation phase in the following way:

  • Tasks are grouped into phases that correspond directly to the user stories defined in spec.md. Each user story phase is independently complete: a developer can stop after any story phase and have a working, demonstrable increment of the feature. This contrasts with a flat task list, where the feature is only testable once all tasks are complete.
  • For every backend user story, the development workflow follows three sequential phases: RED, GREEN, and REFACTOR. The RED phase consists solely of writing tests, which must be confirmed before implementation begins. The GREEN phase covers the implementation itself, bringing all tests to passing. The REFACTOR phase handles route registration, code style enforcement, and static analysis. This three-phase structure is a core workflow principle of the project, ensuring that the test suite accurately reflects intent rather than rationalising existing code.
  • The task list opens with a Setup phase (external dependency installation) and a Foundational phase (database migration, model, factory, policy). These two phases are explicitly marked as blocking: no user story work may begin until both are complete and verified. This prevents the common failure mode where implementation begins before the infrastructure that supports it is in place.
  • Tasks that touch different files and have no shared dependency on an incomplete task are marked [P]. This annotation serves as a signal to both human developers and AI agents that these tasks can be executed concurrently. Within Phase 2 of Feature 014, for example, the model, factory, and policy files can be created simultaneously because they have no mutual dependency.

5.6. Phase 4: Implementation (/speckit.implement)

The implementation phase consumes tasks.md as its primary input and produces source code as its output. Unlike the preceding phases, which are entirely document-producing, Phase 4 is iterative: each task is executed, verified, and committed before the next begins. The AI coding agent operates strictly within the boundaries established by data-model.md and contracts — it is executing a specification, not making design decisions.


The developer (or AI agent) works through tasks.md in the order specified, treating each task as an atomic unit of work (task-by-task execution). A task is not considered complete until its verification command passes. This prevents the common failure mode of implementing several tasks simultaneously and encountering cascading failures that are difficult to attribute to a specific change.

Test-Driven Development (TDD) - each backend user story is supported by accompanying tests.[x] When a task cannot be completed as specified — for example, if an SDK API differs from what research.md documented — the deviation should be recorded in a brief note and the affected research.md entry is updated before proceeding. This keeps the planning artifacts accurate as a record of what was actually built, not only what was planned.

5.7. Relationship to "Vibe Coding"

The contrast with ad-hoc AI-assisted development is most visible at the moment of implementation. In a vibe-coding workflow, a developer would prompt an AI with something like "implement a diet plan generator for my Laravel app" and review the produced code for obvious errors before committing it. The AI makes dozens of implicit decisions — table names, column types, authorization approach, retry behaviour, response shape — without those decisions being documented or reviewed.

In the speckit workflow, every one of those decisions appears in a named research entry, a data-model definition, or an API contract, reviewed and approved by the developer before implementation begins. When the AI generates source code in Phase 4, it is executing an explicit specification — not making creative choices.

This has several practical consequences:

  • Traceability: every implementation decision traces back to a numbered requirement (FR-NNN) or a research decision (D-N). Reviewers and future maintainers can understand why the code is the way it is.
  • Reviewability: because the design was documented before implementation, a code review can check conformance with the approved design rather than trying to reverse-engineer intent from the code.
  • Reproducibility: if the implementation is discarded and rewritten, the specification and plan artifacts survive. A new implementation from the same artifacts will produce equivalent behaviour.
  • Testability: acceptance criteria defined in spec.md become the test assertions in the Pest test files. There is no ambiguity about what "done" means.

5.8. Limitations

The approach described here is not without cost. The specify, plan, and task generation phases add front-loaded effort that would not exist in a direct implementation workflow. For features where the design space is well understood and the implementation is straightforward, this overhead may not be justified.

The AI Diet Plan Generator is a non-trivial case: it introduces a new external dependency - Laravel AI SDK (Laravel AI SDK - Build AI Apps with Laravel, n.d.) , a new architectural pattern (asynchronous agent execution with status polling), and a new security boundary (excluding patients from all AI endpoints). These properties make the upfront investment worthwhile. For simpler CRUD additions to existing resources, a lighter process is appropriate.

A second limitation is that the speckit workflow relies on the AI agent accurately executing the task list without introducing unspecified behaviour. In practice, static analysis (Larastan) and the Pest test suite catch most deviations, but they cannot verify that the implementation fully captures the intent of the original specification. Human review of the GREEN commit against contracts/api-endpoints.md remains a necessary step that the tooling does not automate.

  1. SYSTEM TESTING

6.1. Testing Approach

The NutriBase backend is tested exclusively with automated tests written using Pest 4 (Maduro, n.d.) , a P[y][z]HP testing framework built on top of PHPUnit 12. The test suite runs against an in-memory SQLite database using Laravel's RefreshDatabase trait, which rolls back all database state after each test. This ensures complete test isolation — no test depends on or is affected by the state left by another.

Tests are organised into two categories:

  • Unit tests(Beck, 2003) - e[aa][ab]xercise a single class or trait in isolation, with no database or HTTP involvement.
  • Feature tests (Beck, 2003) - make real HTTP requests against the full Laravel application stack, including routing, middleware, form request validation, controllers, service classes, and the database layer.

The actingAs() helper is used to authenticate requests as a specific user role without going through the login endpoint, enabling direct testing of authorization rules for each role combination. Laravel factories with named states (admin(), doctor(), patient(), hasSocioeconomic()) are used to create test data, keeping tests readable and aligned with the domain model.

Static analysis is performed separately by Larastan at level 5, which catches type mismatches and incorrect return types before the test suite runs.

  1. MAINTENANCE ANALYSIS

7.1. Deployment Architecture

NutriBase is deployed on Railway, a managed Platform-as-a-Service (PaaS) provider. The deployment consists of three services running within a single project:

API Service — the Laravel 12 backend, auto-built by Railway's Nixpacks builder from the backend/ directory. Nixpacks detects the PHP environment, installs Composer dependencies, and starts the application using the built-in PHP server configured via APP_ENV=production.

Queue Worker Service — a separate Railway service running the same Laravel codebase with a different start command (php artisan queue:work --sleep=3 --tries=3). This service processes all asynchronous jobs: GenerateDietPlanJob (AI diet plan generation) and SendDietPlanEmailJob (diet plan email delivery). Separating the worker from the API service ensures that long-running AI inference jobs do not block HTTP request handling.

Frontend Service — the Next.js 15 application, built and served from the frontend/ directory. Railway builds the Next.js project and serves it via the built-in Node.js server.

Railway's PostgreSQL plugin provides the production database. The QUEUE_CONNECTION=database configuration means jobs are stored in the jobs table of the same PostgreSQL instance, keeping the infrastructure simple without requiring a dedicated Redis service.[ad][ae]

All inter-service communication uses Railway's private networking. The INTERNAL_API_URL environment variable on the frontend service points to the API service's private Railway URL, ensuring API calls between the Next.js server and Laravel do not leave Railway's internal network.

7.3 Monitoring and Logs

Railway streams stdout and stderr logs from all three services in real time through its dashboard. Laravel writes structured log entries for security-sensitive events. In production, these logs should be forwarded to a persistent log aggregator (e.g. Papertrail or Logtail) since Railway's in-dashboard log retention is limited.

7.4 Data Maintenance and Backup

Database Backups - Railway's PostgreSQL plugin provides automated daily backups with a seven-day retention window. Point-in-time recovery is available through the Railway dashboard, allowing the database to be restored to any state within the retention window. For a clinical application where data loss is unacceptable, Railway's backup schedule should be supplemented with a scheduled pg_dump export stored in external object storage (e.g. AWS S3 or Cloudflare R2).

Queue Job Persistence - Pending and failed jobs are stored in the jobs and failed_jobs tables in PostgreSQL. If the queue worker crashes, jobs remain in the database and are re-processed when the worker restarts. Failed jobs — those that have exceeded the --tries=3 limit — are written to failed_jobs and can be retried manually via php artisan queue:retry all or inspected and discarded via php artisan queue:flush.

7.5 Crash Recovery

Railway monitors all services and automatically restarts any service that exits with a non-zero code. If service exits unexpectedly Railway detects the failure and restarts the container within seconds.

  1. CONCLUSION

NutriBase was developed as part of a university software design project, targeting a practical gap observed in small-scale nutritional health practices. Independent nutrition advisors and small clinics in this space typically lack access to affordable, integrated software — patient data lives in spreadsheets, diet plans are drafted manually and sent via email, and visit notes are kept in separate documents with no shared structure. NutriBase addresses this directly by consolidating patient records, clinical visits, vital sign tracking, and AI-assisted diet planning into a single platform, purpose-built for the scale and workflow of a small nutrition practice.

Benefits: the decoupled architecture was the right call from day one. A pure JSON REST API on Laravel with a stateless Next.js frontend means the two layers can be scaled, tested, and deployed entirely independently. The Sanctum token model keeps authentication simple without the overhead of OAuth, which is appropriate for a single-tenant clinical tool. The role system  is deliberately lean and has proven easy to reason about as the feature set grew. The most technically interesting part of the system is the AI diet plan pipeline: a queued job dispatches a structured prompt to the OpenAI API, the response is parsed into a typed JSON column, and the result is surfaced to the doctor as an editable proposal rather than a black-box output. This keeps a human in the loop, which is non-negotiable for anything touching clinical decisions.

Lessons learned: designing the OpenAPI contract before writing frontend code was the single best decision in the project. Orval generating a fully typed fetch client from the spec meant that API changes surfaced immediately as TypeScript errors on the frontend rather than silent runtime failures. On the AI side, the most important lesson was prompt stability — small wording changes in the system prompt produce meaningfully different output structures, which breaks the JSON parser downstream. Locking the prompt behind a versioned constant and specifying the response shape before persisting proved essential.

Future work:  the AI diet plan feature is currently the most underdeveloped part of the system relative to its potential. The next meaningful step is retrieval-augmented generation — feeding the model not just the latest vitals snapshot but the full visit history, socioeconomic profile, and flagged anomalies, so the generated plan reflects the patient's actual trajectory rather than a point-in-time measurement. Beyond AI, the platform would benefit from appointment scheduling with conflict detection, PDF export of patient progress summaries, and push notifications for upcoming visits. At the infrastructure level, multi-tenancy support - isolating data per clinic rather than per deployment - would make the platform viable as a hosted SaaS product rather than a self-hosted installation.

Limitations: the AI diet plan output is non-deterministic and must always be reviewed by a qualified nutritionist before clinical use - the system makes this explicit by surfacing plans as drafts requiring doctor sign-off, but the constraint is worth stating clearly. The vital signs model is fixed-schema, which works for standard nutritional metrics but does not accommodate specialist indicators that fall outside the defined fields. File attachment support is absent, meaning external lab results and referral documents cannot be linked to a patient record.
