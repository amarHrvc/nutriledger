# Data Model: SE API Foundation

**Feature**: `001-se-api-foundation` | **Date**: 2026-03-15 | **Plan**: [plan.md](plan.md)

## Entities

This feature introduces one new entity and consumes one pre-existing entity. No domain models
(Patient, Visit) are touched.

---

### Access Token *(new)*

Represents a single authenticated session for one `User`. Issued on login, revoked on logout.

| Field | Type | Notes |
|---|---|---|
| `id` | bigint PK | Auto-increment |
| `tokenable_type` | string | Polymorphic type — always `App\Models\User` for this app |
| `tokenable_id` | bigint | FK → users.id |
| `name` | string | Human label — set to `"auth_token"` on login |
| `token` | string(64) | SHA-256 hash of the raw token — unique |
| `abilities` | json / null | Not used in this feature; Sanctum default `["*"]` |
| `last_used_at` | timestamp / null | Updated by Sanctum on each authenticated request |
| `expires_at` | timestamp / null | Set to `Carbon::now()->addMonth()` on creation |
| `created_at` | timestamp | — |
| `updated_at` | timestamp | — |

**Storage**: `personal_access_tokens` table — generated by `php artisan install:api` migration.

**Lifecycle**:
```
POST /api/login (valid credentials)
  → User::createToken('auth_token', ['*'], Carbon::now()->addMonth())
  → Returns { plainTextToken }

GET /api/user / POST /api/logout (auth:sanctum middleware)
  → Sanctum hashes incoming Bearer token, looks up personal_access_tokens

POST /api/logout
  → $request->user()->currentAccessToken()->delete()
  → Token row removed — immediate revocation
```

**Validation rules**:
- `expires_at` MUST always be set (LARAVEL_API_RULES.md §5)
- Token is invalidated by deleting the row — no soft delete on this table

### User *(pre-existing — consumed, not modified)*

Identified by `email` and `password` (hashed). Has a `role` column (`admin`, `doktor`, `pacijent`).

| Field | Type | Notes |
|---|---|---|
| `id` | bigint PK | — |
| `name` | string | Returned by `GET /api/user` |
| `email` | string | Login credential |
| `password` | string | Bcrypt hash — compared via `Auth::attempt()` |
| `role` | string | `admin` / `doktor` / `pacijent` — enforced by RoleMiddleware |

Only fields returned by `GET /api/user` (FR-004): `id`, `name`, `email`, `role`.
No other User fields are exposed in this feature.

## Response Shapes

These are the canonical shapes for this feature. All API controllers MUST use the `ApiResponses`
trait — no direct `response()->json()` calls.

### Success (HTTP 200 / 201)

```json
{
  "message": "Human-readable description",
  "status": 200,
  "data": { ... }
}
```

### No Content (HTTP 204)

Empty body. Used by `POST /api/logout`.

### Validation Error (HTTP 422)

```json
{
  "message": "The given data was invalid.",
  "errors": {
    "email": ["The email field is required."],
    "password": ["The password field is required."]
  }
}
```

### Unauthenticated (HTTP 401)

```json
{
  "message": "Unauthenticated.",
  "status": 401,
  "data": null
}
```

### Forbidden (HTTP 403)

```json
{
  "message": "Forbidden.",
  "status": 403,
  "data": null
}
```

## State Transitions

```
[No token]
    │
    ▼ POST /api/login (valid credentials)
[Active token]
    │
    ├─▶ GET /api/user  → returns user identity
    ├─▶ GET /api/ping  → returns { status: "ok" } (no token required)
    │
    ▼ POST /api/logout
[Token deleted]
    │
    ▼ Any subsequent request with deleted token
[401 Unauthenticated]
```
