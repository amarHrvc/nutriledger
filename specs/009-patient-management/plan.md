# Implementation Plan: Patient Management

**Branch**: `009-patient-management` | **Date**: 2026-05-04 | **Spec**: [spec.md](spec.md)  
**Input**: Feature specification from `/specs/009-patient-management/spec.md`

## Summary

Implement patient management UI (list, detail, create, edit, deactivate) following the user management blueprint in `_docs/blueprints/user-management.md`. The backend API already exists and requires no changes. This feature is purely frontend: BFF routes + React views.

**Scoping decisions**:
- Patient list shows **active patients only** — no `withTrashed`, no backend change needed
- Patient creation: BFF orchestrates two calls — create user (role=pacijent) → create patient (Q1→A1)
- Lifecycle: **deactivate only** (soft delete via DELETE). Restore is handled via user management — restoring the linked user account also restores patient access.
- `PatientStatusChip` not needed — list and detail only ever show active patients

### FE-1 — BFF Routes: Patient List + Create

**Goal**: Provide `GET /api/patients` and `POST /api/patients` BFF endpoints.

**Inputs**: `frontend/src/app/api/users/route.ts` (reference), Orval clients `patientsIndex`, `patientsStore`, `usersStore`

**Outputs**: `frontend/src/app/api/patients/route.ts` (new)

**Steps**:

1. Create `frontend/src/app/api/patients/route.ts`:

   ```ts
   import { NextRequest } from 'next/server'
   import { patientsIndex, patientsStore } from '@/api/generated/patient/patient'
   import { usersStore } from '@/api/generated/user/user'

   export async function GET() {
     const res = await patientsIndex()
     return new Response(JSON.stringify(res.data), { status: res.status })
   }

   export async function POST(request: NextRequest) {
     const body = await request.json()
     const { name, email, password, password_confirmation, ...patientFields } = body

     const userRes = await usersStore({ name, email, password, password_confirmation, role: 'pacijent' } as any)
     if (userRes.status !== 201) {
       return new Response(JSON.stringify(userRes.data), { status: userRes.status })
     }

     const userId = (userRes.data as any)?.data?.user?.id
     const patientRes = await patientsStore({ user_id: userId, ...patientFields } as any)
     return new Response(JSON.stringify(patientRes.data), { status: patientRes.status })
   }
   ```

2. Verify `usersStore` response shape contains `data.user.id` by checking `frontend/src/api/generated/user/user.ts`.

**Rationale**: Two-call BFF (Q1→A1). User is created first with role `pacijent`; if it fails, patient creation never runs. No backend change required.

**Verification**: `POST /api/patients` with valid payload creates both user and patient. `GET /api/patients` returns patient list.

### FE-2 — BFF Routes: Patient Show + Update + Deactivate

**Goal**: Provide `GET`, `PATCH`, `DELETE /api/patients/[id]` BFF endpoints.

**Inputs**: `frontend/src/app/api/users/[id]/route.ts` (reference), Orval clients `patientsShow`, `patientsUpdate`, `patientsDestroy`

**Outputs**: `frontend/src/app/api/patients/[id]/route.ts` (new)

**Steps**:

1. Create `frontend/src/app/api/patients/[id]/route.ts`:

   ```ts
   import type { NextRequest } from 'next/server'
   import { patientsShow, patientsUpdate, patientsDestroy } from '@/api/generated/patient/patient'

   export async function GET(_: NextRequest, { params }: { params: Promise<{ id: string }> }) {
     const { id } = await params
     const res = await patientsShow(id)
     return new Response(JSON.stringify(res.data), { status: res.status })
   }

   export async function PATCH(request: NextRequest, { params }: { params: Promise<{ id: string }> }) {
     const { id } = await params
     const body = await request.json()
     const res = await patientsUpdate(id, body as any)
     return new Response(JSON.stringify(res.data), { status: res.status })
   }

   export async function DELETE(_: NextRequest, { params }: { params: Promise<{ id: string }> }) {
     const { id } = await params
     const res = await patientsDestroy(id)
     return new Response(null, { status: res.status })
   }
   ```

**Rationale**: Mirrors user BFF exactly. No restore/force routes — lifecycle management is delegated to user management.

**Verification**: `GET /api/patients/1` returns patient JSON. `DELETE /api/patients/1` returns 204.

### FE-4 — `PatientForm` Component (Create)

**Goal**: Form collecting user account fields + patient fields, submits via `POST /api/patients`.

**Inputs**: `frontend/src/views/users/UserForm.tsx` (reference), BFF `POST /api/patients` contract

**Outputs**: `frontend/src/views/patients/PatientForm.tsx` (new)

**Steps**:

1. Create `PatientForm` with two visual sections:

   **Account** (user fields):
   - Name, Email, Password, Confirm Password (all required)

   **Patient info** (patient fields):
   - First Name, Last Name (required, max 50)
   - Date of Birth (`type=date`, required, must be past date)
   - Gender (Select: M / F, required)
   - Phone (required)
   - Emergency Contact Name + Phone (required)
   - Address, City, Postal Code (optional)
   - Blood Type (optional Select: A+, A-, B+, B-, AB+, AB-, O+, O-)
   - Allergies, Medical Notes (optional TextField multiline)

2. On submit:
   - `POST /api/patients` with combined body
   - 422 → bind `json.errors` to individual fields (`errors['name']?.[0]`, `errors['first_name']?.[0]`, etc.)
   - non-ok → top-level `<Alert severity='error'>` banner
   - 201 → `window.dispatchEvent(new CustomEvent('patients:changed'))`, call `onSuccess?.()`

3. Props: `onSuccess?: () => void`, `onCancel?: () => void`

**Rationale**: BFF handles the two-call orchestration — the form treats it as one atomic submit. Error binding covers both user and patient field validation errors since they share the same `json.errors` map.

**Verification**: Missing required fields show inline errors. Valid submit creates patient, list refreshes, dialog closes.

### FE-6 — `patient-left/` — Identity Card + Suspend

**Goal**: Left column showing patient identity and a single deactivate (suspend) action.

**Inputs**: `frontend/src/views/users/user-left/UserDetailsCard.tsx` (reference), `PatientResource` attributes, `ConfirmDialog` (reuse from users/shared)

**Outputs**:
- `frontend/src/views/patients/patient-left/PatientDetailsCard.tsx` (new)
- `frontend/src/views/patients/patient-left/index.tsx` (new)

**Steps**:

1. `PatientDetailsCard.tsx`:
   - Avatar with initials from `attributes.fullName`
   - Full name, gender chip
   - Details section: email (from `relationships.user.data.id` → resolve via included user, or show from the linked user resource), date of birth, phone, member since (`attributes.createdAt`)
   - Stats row: Visits count (placeholder `—`)
   - Single action button: "Suspend" (always shown — detail page only accessible for active patients)
   - Suspend action:
     ```
     openConfirm('deactivate')
     → ConfirmDialog
     → DELETE /api/patients/${patient.id}
     → check res.ok → toast.error on failure
     → toast.success on success
     → router.push('/dashboard/patients')   ← navigate away (patient is now deactivated, detail is inaccessible)
     ```
   - Import `ConfirmDialog` from `@/views/users/shared/ConfirmDialog`

2. `patient-left/index.tsx`: Grid container wrapping `PatientDetailsCard`.

**Rationale**: After deactivation the patient no longer appears in the list and the detail 404s — so navigate away, not dispatch+refresh. No `isDeleted` check needed since this page is only reachable for active patients.

**Verification**: "Suspend" + confirm soft-deletes patient, shows success toast, redirects to `/dashboard/patients`. Cancel leaves patient unchanged.
